4. Google Sheets를 관심 목록으로 연결 / 슬라이드 14–16 · 20분
왜 하나요: 익숙한 표를 앱의 입력 자료로 쓰면 학생이 코드나 데이터 파일을 직접 고치지 않아도 됩니다.
쉬운 이론: 이번 연결은 에이전트가 시트를 읽어 프로젝트 목록에 반영하는 방식입니다. 앱의 새로고침 버튼이 Google 시트를 실시간 조회하는 구조는 아닙니다.
강사 설명: “표는 사람이 편집하는 목록, 앱은 그 목록을 클릭하는 도구입니다. 표의 행이 버튼이 되는 과정을 보세요.”

1. 준비한 ‘리서치 연습 - 관심 목록’을 엽니다. 관심종목 탭의 A1:E3에 열 다섯 개와 회사 두 행이 있는지 봅니다. 가격 칸은 없습니다.
2. X02를 실행합니다. 이름이 같은 문서가 여러 개면 링크를 열어 본인 문서를 고릅니다. 문서 검색을 지원하지 않으면 현재 시트 주소 하나를 보내고 그 문서의 같은 범위를 읽도록 합니다.
3. 읽은 결과가 기본 예시와 같아도 실제 연결 증거를 확인합니다. 문서 링크·범위·읽은 시각이 있어야 합니다. 연결 실패 후 요청문의 두 행을 복창한 답은 성공이 아닙니다.
4. X03을 실행해 두 행을 앱 관심 목록 버튼으로 만듭니다. 화면에서 ‘애플 (AAPL)’, ‘마이크로소프트 (MSFT)’를 찾아 각각 ‘비교에 넣기’를 누릅니다.
5. 기존 가격·비교 기능이 이어지는지 확인합니다. 관심 목록을 클릭했는데 이름만 바뀌고 수치가 같으면 P08로 실제 조작을 전달합니다.
6. 읽기 연결을 더 확실히 확인하려면 시트의 D2 메모를 ‘아이폰 회사 - 확인’으로 직접 바꿉니다. X02를 다시 실행해 변경 문구가 읽히는지 봅니다. 이 작은 변경은 가격·종목 선택에 영향을 주지 않습니다.
7. 앱 반영도 갱신하려면 X03을 다시 실행합니다. 원본만 바꾼 뒤 앱에 자동 반영되지 않는 것이 이번 구조의 한계입니다. 자동 동기화 표시를 붙이지 않습니다.
사용 카드: X02, X03
기대 결과: 원본 시트 두 행이 앱 버튼으로 이어지고 기존 가격 조회·비교를 사용할 수 있습니다.
막히면:
- 한글 회사명이 검색 안 됨: 종목코드 AAPL·MSFT와 한글 별칭 처리를 구분합니다. 시트 코드 오타를 먼저 봅니다.
- 관심 목록에 같은 회사가 두 번 나옴: 시장+종목코드로 중복을 제거하도록 요청합니다. 회사명 철자만 비교하지 않습니다.
- 새로고침했는데 메모가 예전 값: 이번 설계는 읽은 시점의 목록입니다. X02→X03으로 다시 가져오고 새 읽은 시각을 확인합니다.
확인 질문·해설: 에이전트의 Google 권한이 웹앱에도 자동으로 전달되나요? → 아니요. 앱 지속 연결에는 별도 구현이 필요합니다.

5. 보고서 버튼→Google Docs 보관 / 슬라이드 17–18 · 15분
왜 하나요: 같은 자료를 다시 입력하지 않고 확인한 결과를 정해진 문서에 보관합니다.
쉬운 이론: 앱 보고서 버튼은 현재 데이터를 양식에 배치합니다. Docs 연결은 에이전트가 검토한 본문을 문서에 추가하는 별도 동작입니다.
강사 설명: “새 분석을 또 시키는 시간이 아닙니다. 화면의 숫자와 문서의 숫자가 같은지 확인하는 시간입니다.”

1. P07을 실행합니다. 보고서 버튼이 생기면 두 회사를 고른 상태에서 누릅니다. 뉴스가 없으면 ‘뉴스 미연결’이 들어가도 정상입니다.
2. 보고서에서 회사 두 개·실제 기간·마지막 값·USD·출처·조회 시각을 찾습니다. 화면의 한 수치와 시각을 보고서와 맞춥니다. 양식은 채우지만 알 수 없는 숫자는 만들지 않습니다.
3. 인쇄 화면을 열어 한 장의 구성이 보이는지 봅니다. PDF 저장이 필요하면 브라우저의 PDF 저장을 선택합니다. 이것만으로 Docs 저장까지 된 것은 아닙니다.
4. X04로 본인 ‘리서치 연습 - 비교 기록’ 문서와 들어갈 내용을 미리 봅니다. 제목이 같은 문서는 링크로 확인합니다. 보고서 기록 ID를 확인해 같은 내용인지 식별합니다.
5. 본문·대상 문서가 맞으면 X05를 보냅니다. 이 요청에는 확인한 문서에 한 번 쓰겠다는 승인이 들어 있습니다. 대상이 틀리면 이 카드를 보내기 전에 고칩니다.
6. 완료 링크를 직접 열어 두 회사·수치·조회 시각·기록 ID가 있는지 봅니다. 에이전트가 다시 읽은 결과와 브라우저 확인을 같이 기록합니다.
7. 같은 보고서를 다시 보낼 때는 ID로 중복을 확인합니다. 새 조회 결과라면 조회 시각과 ID가 달라져야 합니다. 원본 문서 전체를 덮어쓰지 않습니다.
사용 카드: 07, X04, X05
기대 결과: 앱의 현재 보고서와 본인 Docs 문서의 동일 기록을 대조할 수 있습니다.
막히면:
- 문서 접근 권한 오류: 연결한 계정과 문서 소유자를 확인합니다. 자료를 전체 공개로 바꿔 해결하지 않습니다.
- 보고서의 숫자를 못 읽음: 현재 프로젝트가 출력한 보고서 파일·상태를 읽게 합니다. 학생이 수치를 새로 만들어 채우지 않습니다.
- 문서가 두 번 추가됨: 기존 본문을 임의 삭제하지 않고 기록 ID로 중복 방지 로직을 고칩니다.
확인 질문·해설: 보고서 작성 버튼을 누르면 새로운 AI 모델이 분석하나요? → 이번 구현은 현재 조회 자료를 양식에 배치합니다.

6. Firebase에 비교 기록 저장·다시 읽기 / 슬라이드 19–21 · 20분
왜 하나요: 화면을 다시 열었을 때도 당시 비교 결과를 꺼낼 수 있어야 반복 도구로 쓸 수 있습니다.
쉬운 이론: Firestore는 기록 보관함입니다. 에뮬레이터는 로컬 연습 환경입니다. Firebase MCP는 AI의 개발 도구 연결이며, 실제 앱 저장은 별도로 구현해야 합니다.
강사 설명: “Docs는 사람이 읽는 문서, Firestore는 앱이 다시 읽는 기록입니다. 둘 다 저장이지만 다시 사용하는 방식이 다릅니다.”

1. X06을 실행합니다. 강사가 준비한 demo-study-desk 연습 프로젝트·에뮬레이터 상태를 확인합니다. 학생은 Firebase Console에서 새 운영 프로젝트를 만들거나 결제를 연결하지 않습니다.
2. 연결 화살표를 읽습니다. 브라우저→기존 앱 서버→로컬 Firestore입니다. 원격 실습에서 학생 브라우저의 localhost는 학생 PC를 가리키므로 원격 에뮬레이터 주소로 착각하지 않습니다.
3. X07을 실행해 ‘비교 기록 저장’ 버튼을 만듭니다. 저장 내용은 회사·기간·값·단위·출처·조회 시각·저장 시각·기록 ID입니다. 키나 개인 계좌 정보는 필요 없습니다.
4. 현재 비교 자료를 저장합니다. 저장 중→완료로 바뀌는지 봅니다. 강사 또는 에이전트가 실제 저장소에서 같은 기록 ID를 다시 읽어 보여줍니다.
5. 동일 조회 결과로 저장을 한 번 더 눌러 봅니다. 기록이 두 개가 되지 않아야 합니다. 새로 조회한 다른 결과는 새 기록입니다. 단순히 회사코드만 ID로 쓰면 과거 기록을 덮으므로 구분합니다.
6. X08을 실행하고 페이지를 새로고침합니다. 저장 목록에서 동일 회사·기간·ID를 찾아 누르고 이전 값 하나가 같은지 봅니다. 메모리에 남은 카드만 보여 주는 것은 저장 검증이 아닙니다.
7. 화면에 ‘로컬 Firestore 연습 저장소’와 ‘저장 당시 기록’을 표시합니다. 에뮬레이터가 종료되면 별도 보존 설정 없이는 기록이 사라질 수 있습니다. 브라우저 새로고침 성공을 영구 클라우드 보존으로 설명하지 않습니다.
사용 카드: X06, X07, X08
기대 결과: 실제 로컬 Firestore에 쓴 기록을 페이지 새로고침 후 다시 읽습니다.
막히면:
- 저장 버튼이 완료지만 기록이 없음: 쓰기 응답을 확인하고 성공 후에만 완료 표시하도록 수정합니다.
- 연습 서버 연결 실패: 강사가 같은 서버에서 실행 상태·설정 ID·주소를 확인합니다. 임의로 운영 클라우드로 전환하지 않습니다.
- 새로고침 때 사라짐: 브라우저 변수로만 저장했는지 확인하고 Firestore 읽기 요청을 점검합니다.
- 에뮬레이터를 껐다 켜니 사라짐: 이번 완료 기준은 브라우저 새로고침입니다. 종료 보존은 강사의 별도 export/import 준비 항목입니다.
확인 질문·해설: Firebase를 켜면 주가도 자동 제공되나요? → 아니요. 가격 제공처와 저장소는 역할이 다릅니다.

7. 커스터마이징을 실제 반복 작업으로 / 슬라이드 22의 8분 + 26의 4분
왜 하나요: 똑같은 점검 요청을 계속 길게 쓰지 않고 순서를 저장해 다시 실행합니다.
쉬운 이론: 규칙은 항상 지킬 기준, 스킬은 작업 순서, 예약은 실행 시점입니다. 수동 실행에 실패한 절차를 예약해도 저절로 해결되지 않습니다.
강사 설명: “자동화의 첫 시험은 매일 실행이 아니라, 지금 한 번과 2분 뒤 한 번이 같은 일을 하는지입니다.”

1. X09로 ‘리서치 점검’ 절차를 저장합니다. 시트 읽기→앱 목록 대조→최근 기록의 출처·시각 확인→결과 표의 순서입니다. 설치된 환경에서 실제 스킬 경로·호출 방법을 확인합니다.
2. X10으로 지금 한 번 실행합니다. 시트·앱·기록이 실제로 읽히는지, 대상·시각·결과·이유 네 열이 있는지 봅니다. 이 절차는 자료를 수정하지 않습니다.
3. Remote Agents와 로컬 프로젝트가 분리되어 있으면 로컬 앱을 직접 읽을 수 없을 수 있습니다. 강사가 프로젝트의 비민감 목록·보고서 사본을 명시적으로 제공한 경로를 사용하고 ‘내보낸 시점 자료’라고 표시합니다. 런타임 앱 점검 성공으로 과장하지 않습니다.
4. 수동으로 성공한 동일 범위에만 X11을 사용합니다. 2분 뒤 1회이며 외부 발송·문서 추가·반복 등록이 없습니다. 예정 시각·시간대·예약 ID를 확인합니다.
5. 계속 기다리는 대신 슬라이드23에서 P09 개선을 진행합니다. 대화와 실행 환경을 유지합니다. 등록 안내만 보고 자동화 완료로 체크하지 않습니다.
6. 슬라이드26에서 X12를 실행합니다. 실제 실행 시각과 결과 표를 확인합니다. 예약이 실행됐으나 자료 읽기에 실패했다면 두 상태를 나누어 적습니다.
7. 종료 시 이번 수업의 해당 1회 예약만 확인합니다. 대기 중이면 X12의 허용 범위로 취소하고 다른 예약은 건드리지 않습니다. 장기 Automations·Calendar·Apps Script는 아래 역할 비교로만 다룹니다.
사용 카드: X09, X10, X11, X12
기대 결과: 저장한 점검 절차의 수동 결과와 1회 예약의 실제 실행 결과를 구분합니다.
막히면:
- 스킬 파일이 있지만 호출 안 됨: 현재 제품이 읽는 경로·이름을 확인합니다. 기본 문서를 저장한 것만으로 스킬 등록 성공이라 하지 않습니다.
- 예약 메뉴·명령이 없음: 수동 점검 결과를 남기고 자동화는 미실행으로 기록합니다. 지원 여부는 강사 사전 점검 항목입니다.
- 예약은 실행됐지만 표를 못 읽음: 실행 환경·권한·자료 경로가 수동 때와 같은지 봅니다. 실패를 성공으로 바꾸지 않습니다.
확인 질문·해설: 매일 실행 예약보다 수동 1회가 먼저인 이유는? → 실제로 가능한 절차인지 확인하기 위해서입니다.

다른 Google 기능까지 엮는 방법 / 역할을 고르는 비교 자료
기본 3시간에는 Sheets·Docs와 로컬 Firestore 저장, 1회 예약을 직접 다룬다. 아래는 같은 앱에서 필요한 경우 고를 응용 설계 예시이며 추가 등록을 요구하지 않는다.

Google Drive: 수업용 시트·문서를 ‘리서치 연습’ 폴더에 모으면 다음에 찾기 쉽다. 현재 수업에서는 본인 Docs 링크를 열어 보관 위치를 확인한다. 폴더 이동·공유 변경은 별도 작업이다.
Google Calendar: 다음 주 검토 시간을 사람에게 알려 주는 용도다. 일정 제목 예시는 ‘두 회사 리서치 기록 확인’, 설명은 ‘관심 목록을 확인하고 최신 기록의 출처와 날짜 점검’이다. 일정 알림만으로 앱이 데이터를 갱신하지는 않는다. 실제 날짜·시간·시간대를 정하기 전에는 등록하지 않는다.
Google Slides: 검증한 보고서로 ‘비교 대상 / 기간 변화 / 미확인 사항’ 3장 발표 자료를 만드는 응용이다. 가격을 새로 예측하지 않고 보고서의 동일 자료와 기준 시각을 쓴다.
Antigravity Automations: 대화를 넘어 반복 점검을 실행하는 응용이다. 이번 수업의 /schedule 1회 예약과 수명이 다르다. 실제 실행 환경·권한·비용·실행 이력·중단 방법을 확인한 뒤 같은 점검 절차를 재사용한다. PC가 꺼져도 돌아간다고 확인 없이 약속하지 않는다.
Apps Script: Google 표를 중심으로 반복 업무를 실행할 때 선택할 별도 방식이다. 예를 들어 매주 ‘사용=예’ 행 수를 점검해 같은 시트의 점검 탭에 기록할 수 있다. 시간 기반 트리거는 권한·할당량과 실패를 확인해야 한다. 에이전트 예약과 동시에 이중 등록하지 않는다.
Firebase Hosting: 완성 화면을 제공할 때 쓰는 기능이다. 검색 서버·비밀 관리·운영 저장 권한은 별도이며 정적 화면을 올리는 것만으로 전부 연결되지 않는다.
운영 Firestore: 여러 기기·사용자가 같은 기록을 쓰려는 단계에서 검토한다. 사용자 인증·기록 소유자·접근 규칙·비용·허용/비허용 접근 시험을 준비한다. 연습 에뮬레이터의 열린 접근을 운영에 복사하지 않는다.

선택 기준 예시
사람에게 시간을 알려야 함 → Calendar.
AI가 자료를 읽어 점검표를 만들어야 함 → 수동 검증한 절차 + 지원되는 에이전트 예약.
시트 안에서 단순 집계를 반복해야 함 → Apps Script.
앱에서 저장한 기록을 다시 읽어야 함 → Firestore.
기능이 많다는 이유로 모두 연결하지 않는다. 이번 앱의 실제 불편을 줄이는 역할을 고른다.
